# Persona Workspaces

Use this contract when building or updating persona apps, workspace switching, invitation flows, or subscriber-facing coding-agent tools. This is a runtime instance of one existing persona, not a new public persona, business company, evaluation environment, or AI-resource runner workspace.

## Identity and onboarding

Use `personaWorkspaceId`; never overload `workspaceId`, `companyId`, page ID or a harness workspace ID. The persona page/slug remains unchanged. Every workspace has its own resource bindings and data scope. Its owner and members share operational records, playbook runs, Signals, Data Feed, Media, ROI and audits. Profiles, Coach conversations, personal memory and credentials remain private to the acting user.

People-matching role/profile context is personal and must agree between the header, dashboard and commands. In a workspace request, resolve the acting user's existing profile from the independent published participant pool, outside operational workspace scope; do not look for it in the workspace's cloned list or substitute the owner/billing user. Read this context without migrations or profile writes. Apply its selected role to the workspace's operational view without copying personal answers into shared rows or changing that view's data partition. An already selected role with incomplete optional details must open the dashboard. Keep a genuine role-selection gate for users who have not selected a role, and keep network discoverability/consent checks intact. Test Owner and Member actors, switches between workspace bindings, incomplete optional profiles, fresh role changes, and no writes or cross-user profile disclosure.

Successful people-matching profile/role writes broadcast `people-matching-profile-updated` with the acknowledged persona/context. Profile consumers apply that response immediately and discard pre-save requests. Runtime/catalog caches invalidate before consumers refresh, so role changes or completion never require a browser reload and stale requests cannot reintroduce the gate. Keep this event separate from generic profile-context payloads.

Personal profile context, profile writes, visibility and `people-matching/active-mode` requests must not inherit workspace headers. Server-side role/profile writes also resolve the trusted acting user's independent participant pool if an older client supplies workspace context. Members may update their own profile; owner/billing identity never grants access to the owner's personal profile or lets the member activate it. These personal writes must not create shared workspace profile copies.

Creation requires a name and description. Website is optional. Reuse the avatar picker and image upload; use a supplied website's favicon when no icon was chosen, otherwise an automatic avatar. The creation label defaults to **New Workspace** and is model-configurable.

Users starting their own workspace complete workspace setup in Complete Profile. Preserve and adopt their existing personal records during the one-time migration. Inviting a user NEVER creates another workspace, repository or branch: an invitee with no workspace uses the invited workspace as their default; an existing default stays unchanged. A personal workspace is created only when the user explicitly requests it.

Migrate existing planning goals and boards before creating default planning contexts. A retry may already have seeded workspace defaults: retain those records, demote only their default flags when legacy defaults exist, and preserve the legacy IDs, task relations and timestamps. Keep the unique default indexes enabled and test migration with them; do not delete records or bypass activation to recover a failed migration.

Legacy Git-backed pages may lack stored publication-pin metadata. Resolve their published payload and immutable commit together through the read-only Git resolver, then use that commit throughout provisioning. Reject draft-only or unpinned sources. This compatibility path must never bypass candidate publication gates for quality-schema-v2 personas.

For workspace-enabled apps, show mandatory workspace setup FIRST, with its own title and only the workspace fields. While `workspaceSetup.required` is true, hide Close, Skip and Finish later; block Escape, backdrop dismissal and mobile back navigation. Submit workspace metadata independently of optional questionnaire answers (`complete: false`, empty incoming `answers`, `workspaceSetup`), preserving stored personal answers. Keep setup open on failure or a response that still requires workspace setup. Repository/model provisioning can continue after workspace membership is established.

After the server confirms `workspaceSetup.required: false`, show authored personal questions as a separate OPTIONAL profile step with Close and Skip for now. Skipping does not mark unanswered questions complete and does not create another workspace. Required questionnaire fields are validated only when the user chooses Complete profile. Invitees with a workspace go straight to the optional personal profile; joining never creates extra branches. Keep legacy profile-only personas' existing completion contract. Web, branded desktop and mobile must use this same distinction.

Onboarding belongs only to the authenticated published persona Chat App. Author playgrounds, `/workspace` routes (including `/workspace/edit-persona`), and chat-only PageViewContent/author embeds must not fetch workspace/profile onboarding or request its modal. Cancel pending modal requests on route changes. Save responses are authoritative: broadcast their updated context, invalidate in-flight pre-save reads, and update the gate immediately without requiring refresh. Older profile/catalog reads must not resurrect mandatory setup or publish an error in an unrelated editor.

The first compulsory personal workspace is available without a Business/Team subscription. Every additional workspace, every member invitation (including to the default workspace), and new invitation acceptance require the workspace owner's active Business/Team entitlement. An invitee does not need their own paid plan to join. Team membership qualifies only when active and backed by the team's owner's paid plan. Incomplete checkout, expired/cancelled/past-due plans, personal paid plans, credits and `team:manage` permission alone do not qualify. The server returns `WORKSPACE_TEAM_PLAN_REQUIRED` (402); browser, REST and MCP use the same gate. Recheck on additional-workspace retry and shared execution boundaries. A downgrade preserves stored records and allows member removal/revocation, while blocking new team operations. Never create branches or send invitation emails before eligibility passes.

Configure the persona-themed upgrade popup in Publish → Workspaces or `assets/chat-config.json` → `publishedConfig.personaWorkspaces.upgradePrompt`: optional `title`, `subtitle`, `description`, up to six `benefits`, and `buttonLabel`. `{persona}` inserts the persona's name. Persona upgrade actions (including Explore Business plans in workspace settings and gated New Workspace) open the existing plan-purchase modal directly with the selected persona name, logo, palette and authored copy. Skip Gabriel organization creation, Business onboarding and Team Info forms for this persona upgrade. Opening pricing must not create a company, persona workspace, branches or invitations. Preserve the existing billing plan, API pricing and payment confirmation; do not hardcode prices or configure a checkout URL. General Gabriel business-workspace creation keeps its separate organization setup flow. The plan gate is not configurable. Settings are author-only, revision-checked and Git-synced; subscriber workspace edits cannot change them.


Opening a persona page, author playground or chat-only embed must remain read-only: do not auto-provision AI Resources, replay a saved runner provisioning preference, or open a runner Git dialog during startup. Request runner setup only from an explicit resource action or a genuine runner command preflight; an empty model response or `WORKSPACE_NOT_READY` is not a runner setup error. Operational requests carry persona workspace context; account preferences, author configuration, profile onboarding, channel launchers and `/api/harness/personas/...` do not inherit it. Match `/api/personas/...` explicitly rather than any nested `/personas/...` URL.

Saved workspace metadata completes the mandatory form, while repository/model provisioning remains a separate state. Gate operational views until the selected workspace is ready, showing provisioning progress or an actionable failure with owner-only Retry. Do not reopen mandatory profile setup for an existing failed workspace or fall back to the author's runtime data. Persist retry status before acknowledging it, bypass shared database caches for discovery/status reads, and invalidate bootstrap/runtime reads when setup becomes ready so the app recovers without refresh. Verify the actual server-held Git credential identity through the provider's authenticated identity endpoint and its repository permissions. Cached connection usernames can be stale after account changes; local CLI authentication can belong to another account. Git permission failures require the author's connection to have write access to every bound dependency (including landing/app repositories); never ask a subscriber to fix author Git access. Keep failing stage and sanitized repository diagnostics server-side, and expose no credentials or raw provider errors. Internal author-authenticated imports must reuse the workspace owner’s existing list/pipeline projections. Translate author identity only for definition queries within the trusted provisioning context; never extend that translation to runtime records or normal author requests. Verify repeated import preserves resource/collection IDs and rows without ambiguous duplicate bindings.

## Author-owned definitions and private runtime data

Keep navigation reads proportional to their purpose. Membership, visibility and workspace discovery use metadata projections; do not transfer stored initialAssets, assets or runtimeConfig when checking access or rendering workspace selectors. Reuse one projected pinned-definition read within the authorized request/execution, including page overlays and runtime resolution. Key reuse by its immutable context and preserve captured revision lookups; missing historical revisions must fail instead of falling back to current assets. Keep authorization, membership and status checks fresh across requests, and isolate presentation adaptations between consumers. Metadata-only page/automation projections must not attach full configuration overlays. Full workspace page reads omit the author publishedConfig that the pinned workspace definition replaces, while preserving separate voice settings. Catalog browsing projects schemas and pins without retained workflow bodies; explicit detail/execution requests retain full structures. Read registered, workspace-pinned Data Feed definitions without re-importing them during navigation; provisioning and validated definition updates perform synchronization before activation. Pinned definition content may use a bounded, short-lived cache keyed by database collection identity, persona/workspace, owner, captured revision, repository pins and workspace update stamp. Re-read live status/revision metadata on each authorized request/execution context; check historical snapshot existence even when its content is cached. Inactive/deleted workspaces and missing history fail closed. Never cache membership, permissions, personal presentation or runtime rows. Clone configurations for consumers, coalesce only content reads, and bound TTL, entry count and bytes. Repair/update stamps invalidate the content key. Measure repeated workspace reads and response timings when investigating slow menus.

Startup and reload must share one bootstrap per actor, authentication generation, persona, selected workspace and language. Learning the first workspace/definition/profile revision is response metadata, not a scope change; invalidate on an actual revision change or acknowledged edit. Retain bounded definition caches through layout remounts and coalesce acknowledgement/reconnect notifications. Additional mounts must not clear a workspace already selected in the document, and repeated readiness notifications for its known revision must not invalidate it. Use one visibility recovery path; hidden browser tabs must not open/reconnect realtime streams, while desktop windows retain their stream. Never probe another dashboard to choose a default when the URL, authored default or Coach already determines the destination. Embedded Coach is chat-only and must not bootstrap another app, load connection graphs or prefetch operational catalogs. Authenticated app startup defers the Git-backed connection index until its controls or composer are used; legacy standalone chat retains its established index behavior. Wait for workspace discovery before operational startup reads. Apply its selected workspace before mounting ready child views: child passive effects run before parent effects. First readiness discovery joins the pending scoped bootstrap; an actual provisioning recovery refreshes repaired bindings. Essential persona metadata, workspace discovery and bootstrap reads can use a high fetch scheduling hint ahead of background traffic; retain credentials, cancellation and permission checks. Browser discovery may request includeRuntime=true with language/client capabilities and an optional personaWorkspaceId. Include only that selected ready instance’s freshly authorized bootstrap, tagged with workspace ID and revision; other instances remain metadata only. Seed this bootstrap after applying selection and before mounting child views. Reject mismatched actor/workspace claims, and never cache an authorization decision. Keep role/setup discovery available without an app when configuration is unavailable; permission denials still fail. An initial realtime replay reset must not discard an in-flight or freshly loaded definition; normal data reconciliation and genuine definition/role changes still run. Resolve profile definitions once per context read, and do not request a legacy Git pin merely to display workspace discovery; creation and reviewed updates still require strict immutable pins. Bound optional Coach memory retrieval and cancel a timed-out remote request so provider outages cannot indefinitely hold Home. Verify request counts and cold reloads in addition to warm navigation, including legacy implicit defaults, hidden tabs and workspace/auth changes.

Client workspace/profile invalidation may cancel an in-flight read with AbortError. Discard its result and quietly reload the current context; do not display internal cancellation text such as Chat scope changed. Cancel queued retries when the view departs or a newer request supersedes it. Genuine authorization and network failures must still surface.

`publishedConfig.personaWorkspaces` declares `enabled`, `newWorkspaceLabel`, `generationPrompt`, `allowedAssetPaths`, optional `memberLimit`, and `allowPrivateRepositories` (false by default). Author the generation instructions for the actual persona domain; retain logical resource keys, executable capabilities and approval checkpoints. Use the persona's configured model, not a hardcoded provider/model. The existing Auto setting resolves through the author's configured default model. Declare editable list definitions and exact feed asset paths in allowedAssetPaths; preserve the portable Chat App envelope and mirror its chatApp field into publishedConfig.chatApp.

Send only editable definition context to workspace generation. Project chat-config inputs to firstMessage, workspaceContext and chatApp plus portable envelope identity; exclude draft/published landing translations and protected model, system-prompt and tool configuration. Keep the complete originals for server validation and merging. For dashboards, supply displayText maps keyed by existing JSON pointers; accept only provided string paths and apply them to the original layout. Do not let generation replace component/provider types, actions, identifiers, navigation or data references. This internal generation representation does not change the owner’s validated definition-update API. Correction feedback includes schema paths and messages, with at most one corrective attempt. Reducing the prompt must not broaden edit permissions, replace the configured model or accept an unvalidated partial result.

The service branches the complete bound definition graph using author credentials held on the server. Branch names include the workspace-name slug and an immutable ID. Renaming does not rename branches or identity. Private subscriber repository copies are available only when the author explicitly enables that hosting option. Do not expose author Git credentials or make subscribers clone author repositories manually.

Git contains definitions and configured workspace context, not runtime rows, private chats, files, API keys, credential values, enabled schedules, approval records or execution history. Creation starts with independent data and no executed playbooks or enabled schedules. Branching alone is not data isolation: every list/pipeline/resource is resolved through the workspace's environment-local bindings.

Browser discovery may project the selected workspace’s protected accepted personaWorkspaces policy for display without fetching the author repository. This does not authorize edits or invitations: those commands still validate the current strict author policy. Full persona metadata GETs remain read-only for owners and subscribers alike; never ensure branches, clone full repositories or migrate definitions during page hydration. Preserve current page authorization and sensitive-field stripping before responding. Separate browser connection queuing, server response time, code loading and first usable rows when validating performance. Include total request duration because nested read/definition stages omit earlier middleware and must not be summed as independent work. Measure normal foreground navigation and reloads with DevTools closed; report a separate instrumented sample and the first reload after a server restart. Verify the actual served build and keep its mounts stable across concurrent tasks. Concurrent builds can distort local acceptance measurements; report them instead of treating a successful build as a latency sign-off.

Operational app pages must not mount the closed legacy chat starter or unused author Output, Applications and Quality panels behind their visible dashboard. Load legacy panels on first opening and retain them afterward to preserve unsaved edits. Decide from active/visited tabs, independent of App configuration readiness, so early fallback renders cannot start those reads. Embedded Coach also defers unused legacy panels and channel discovery. Delay optional composer playbook/source catalogs until the visible page's actual data read settles or the user opens chat or its controls. Definition discovery and period initialization alone are not data readiness. Readiness is scoped to actor, persona and workspace; canceled or stale reads never release another scope. Give visible data queries a high browser scheduling hint while preserving workspace headers, credentials and cancellation. Preserve public and standalone chat starters, embedded Coach and explicit New Run flows. A local source mount does not update compiled code: verify the served frontend asset identity and executed backend directory before measuring startup. Use the local build Compose overlay with completed build directories, and preserve runtime data when recreating the API.

Authenticated persona HTML documents and explicit `appView=page:...` URLs serve the static app shell without awaiting public SEO, Git or marketing first-paint preparation. Document navigation may lack the bearer token that authenticates API fetches, so an explicit App destination also selects the shell. Route/cookie/bearer hints grant no data access; authenticated APIs still validate current access. Keep these responses private/no-store and noindex, preserve anonymous landing SEO, reject malformed/multiple App destinations as hints, and verify document response time separately from application data readiness.

Private profile-role display reads may reuse a previously verified author definition while its mutable Git head refreshes. Apply this explicitly to the personal profile GET, which intentionally carries no operational workspace headers. Both the general questionnaire and matching-role GETs need this boundary. The general form checks fresh membership/workspace existence for setup, without repeating full workspace discovery, team billing or app bootstrap. Browser display reads must not run repeated legacy profile or lead migrations; onboarding mutations retain recovery and migration. Generic profile/history visibility checks should project current authorization metadata instead of fetching the full persona definition. Read only access/release provenance, prepared model identity and the published profile contract for this server-only lookup; omit unrelated landing translations and draft voice configuration. Preserve fresh page visibility and actual-actor membership checks. Do not persist source-ownership metadata while resolving a display-only read. Read the acting user's current role and private profile records each time, outside operational workspace scope. Cold reads must verify the source; never substitute an unverified Mongo snapshot or wrong published revision. Exactly verified commit definitions can remain cached until explicit invalidation. Browser definition caches can span ordinary menu switches for a bounded few minutes, keyed by actor/authentication, persona, workspace, language and invalidation epoch. Invalidate on acknowledged changes and recover from server revision conflicts; every data query still rechecks current access. Keep execution, consent, membership and credential/policy decisions on strict current reads; display caching must not broaden authority.
Media-provider catalogs, style-guide knowledge bases, library assets, movie projects, cart-note hydration and AI-resource runner status must also wait for actual chat/library controls in an authenticated app. Do not eagerly run these effects merely because a hidden composer or embedded Coach mounted; rendering a panel lazily does not automatically suppress effects in its parent. Keep standalone-chat behavior and refresh results after the user opens the relevant control.


Do not preload every playbook's Operator intake overlay, voice-task discovery/usage catalog or starter repository badges during closed App navigation. Fetch operational catalogs on an explicit chat/run interaction and repository badges when their starter UI opens. Recognize the App host from authenticated App intent/explicit page navigation as well as profile-host flags, before runtime configuration settles. Embedded Coach must never preload operational intake or voice-task catalogs. Initial data readiness must precede optional catalogs; compare browser request duration with Server-Timing to identify connection contention from hidden consumers.

An empty Coach review uses the persona's authored guidance and deterministic starter questions. Do not search remote memory or generate paid welcome copy when there is no completed evidence/session to review. Retain evidence-based personalized generation and bounded optional memory reads for substantive completed work, with private actor/workspace cache keys.

Root policies can contain more than 16 explicit assets, particularly feed definitions. Use `readWorkspaceRootAssets` for bounded reads pinned to one immutable revision during provisioning, template review and definition-retry checks. Preserve the Git adapter's path/traversal limits; do not raise its global limit or replace pins with mutable branch heads.

Generation may edit only firstMessage, workspaceContext and chatApp inside publishedConfig; persona identity, system prompt, model settings, commands, tools and author policy remain unchanged. Put client details in workspaceContext and allowed descriptions. Validate each complete candidate against the original assets before writing it. One corrective model attempt may use validation feedback; it must keep the same author model resolution, audit/billing context and allowed paths. Author-template updates require owner review, preserve customizations, and report conflicts rather than overwriting them. Review returns changedPaths and conflicts; apply with keepCustom: true explicitly preserves conflicting custom settings. New author dependencies receive their own workspace branch before activation. ## Roles, invitation and spending

Only **Owner** and **Member** are supported. Owners manage membership/settings and permitted definition edits. Members run playbooks and manage shared operational records; they cannot edit definitions, configure Signals/Routines/feeds, manage membership, or become persona administrators. Enforce these rules server-side; prompts and hidden buttons are not authorization.

Verified users already registered for the persona join directly. Others receive a persona-branded, seven-day invitation and sign in/register with the invited email. Tokens are single-use, hashed, revocable and resendable. Membership, invitation acceptance, default selection and declared seat admission must commit transactionally. MongoDB session reads must bypass process-wide query caching and deduplication: each transaction uses its own snapshot, and ClientSession objects must not enter cache-key serialization. Do not invent a ten-seat limit when no limit was authored.

Shared runs use the workspace owner's persona entitlement and credits. Retain `actorUserId`, workspace owner, definition author and billing user separately. Do not impersonate the owner or grant members card/Guardian approval rights. Removing membership invalidates future calls, bound keys and subsequent execution steps.

## APIs and agent connections

Browser/session API root: `/api/agent-configs/user/pages/{pageId}/persona-workspaces`.

- Author-only `GET /editor`, `PUT /configuration` read/save the portable `personaWorkspaces` policy with `expectedRevision`. Discovery returns `access.teamPlan`, `access.canCreateWorkspace` and resolved `upgradePrompt`; Team returns separate `canManage` and `canInvite` flags.

- `GET` discovers owned/member workspaces and default/selected preference; `POST` creates with an idempotency key.
- `POST /{id}/select`, `PATCH /{id}`, `POST /{id}/retry` select, update metadata and retry setup.
- `GET /{id}/team`, `POST /{id}/invitations`, `DELETE /{id}/members/{userId}`, `DELETE /{id}/invitations/{invitationId}` manage the team.
- `POST /invitations/accept` accepts the authenticated, email-matched invitation. Branded email links open /invites/persona-workspace/{token}, which uses personaPageId with the standard login/signup modal before email-matched acceptance. Public invitation preview reveals no recipient email or runtime records.
- `GET /{id}/definitions`, `PATCH /{id}/definitions` describe/edit author-permitted assets. Supply `expectedRevision`; `validateOnly: true` previews without writing.
- `POST /{id}/template-updates/review` and `POST /{id}/template-updates/{proposalId}/apply` review/apply template updates.

Gateway REST uses `/api/gateway/pages/{pageId}/workspaces`. Discover through `gabriel_list_persona_workspaces`, create through `gabriel_create_persona_workspace`, and use `gabriel_get_persona_workspace_definitions`, `gabriel_update_persona_workspace_definitions`, `gabriel_get_persona_workspace_team`, `gabriel_invite_persona_workspace_members`. Use gabriel_update_persona_workspace, gabriel_remove_persona_workspace_member, gabriel_revoke_persona_workspace_invitation, gabriel_review_persona_workspace_template and gabriel_apply_persona_workspace_template for metadata, team and reviewed-template maintenance. Persona-bound equivalents use persona_update_workspace, persona_remove_workspace_member, persona_revoke_workspace_invitation, persona_review_workspace_template and persona_apply_workspace_template and cannot target another persona. Use app-read/app-write scopes; definition edits and invitations additionally require workspace ownership.

Bind new persona API keys and agent connections to the selected workspace. OAuth resources use /mcp/persona/{pageId}/workspaces/{personaWorkspaceId}; consent/token refresh revalidates membership. A private persona invitation does not make it public. Carry `x-persona-workspace-id` and `x-persona-page-id` on operational REST requests. A conflicting workspace ID must fail. Legacy requests resolve only the authenticated default; never choose a random workspace. Preserve workspace identity and definition revision through queues, callbacks, retries and worker recovery. Switching the UI must not retarget an in-flight execution.

## App composition and ROI

Use the standard sidebar switcher with Owner/Member labels. Put a settings action beside each owned workspace row; Members get a read-only team action for that row. Settings include a styled Invite members disclosure, collapsed by default, with member count, invitation form and team management subject to server permissions. Capture the target workspace when opening a dialog: loading members, invitations, metadata saves and template updates must all use that ID even when another workspace is selected. Discard stale responses after closing or opening a different workspace dialog. Keep Home's Coach/domain tabs, sidebar Playbooks, standalone sidebar ROI, and inner Signals/Planning controls. Never add duplicate Home or Signals navigation tabs.

Use the shared Modal/BaseModal or Radix Dialog components and the app's ModalStackProvider. Keep each backdrop and foreground in the same portal frame; backdrops use local layer 0 and panels/scroll containers use layer 1. The shared stack also tracks custom persona portals, so do not fix nesting with escalating hardcoded z-indices. Use an opaque persona surface on themed modal cards, and preserve mandatory-workspace dismissal rules and optional-profile skipping while allowing child icon/calendar dialogs to handle their own keys.

Namespace cache keys, conversation drafts, schedules, media, realtime invalidations and ROI baselines. Notifications target current members, not the persona author merely through authorship. Value comes from accepted, deduplicated ontology-linked output evidence. Investment comes from the SAME workspace's consumed tokens/credits. Funding and provider cost remain separate; do not count a shared wallet top-up in each workspace's return.
